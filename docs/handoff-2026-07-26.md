## 6. 已知风险与未完成边界

### 6.1 接手后优先复核

1. **P1：schedule contract 最新项可能选错。** `schedule_contracts.py` 和 schedule pipeline 按
   TEXT `observed_at` 排序，但 `_timestamp` 使用可变宽 ISO 文本。同一秒的 `...00Z` 在降序排序时
   可能排到实际更晚的 `...00.500000Z` 前，导致错误选择旧合同，并破坏“latest invalid 不回退”。
   当前测试没有同秒微秒边界用例；恢复后应先写失败测试并统一可排序时间表示或改用可靠比较。
2. **P1：source-policy 权威边界未定稿。** `allowed_hosts=()` 当前会放行任意 host，golden 也使用
   空 host；同时 `created_at` 不参与 formal boundary 判断。需要明确离线 fixture 特例、生产 official
   policy 是否必须 host-bound，以及是否允许追溯授权，然后补伪造域名和时间边界负测。
3. v7 -> v8 -> v9 是否对新库、真实 v7 库、真实 v8 库都原子、幂等且 fail closed。
4. 伪造同名表、缺少约束、错误 trigger body、部分迁移和失败回滚是否被拒绝。
5. mapping/source-policy 的 CAS、append-only、撤销和半开边界是否与 formal/audit 语义一致。
6. official-lineup v1-v4、match-report v1-v2 与 schedule contract 的联合迁移和 replay。
7. cache entry 是否绑定文件证明和单一 SQLite snapshot；调用方变异、WAL 并发和失败逐出是否安全。
8. golden run manifest 是否直接固定 schedule/report/lineup contracts，而不是只依赖间接引用。

## 8. 不可破坏的不变量

- raw/canonical/derived 严格分层；raw 不可变且内容寻址；模型不解析来源 HTML。
- 平台 ID 稳定，显示名/provider ID 不能作为下游 join key。
- 所有知识边界使用 timezone-aware UTC，且 `known_at <= as_of`。
- 历史证据只能是 `reconstructed`；`captured` 只能来自可信 prospective capture-run。
- 三种 readiness 独立计算；禁止全局可写 `ready` 和缺失填零。
- baseline、lineup delta、match context 分开计价，同一贡献键只能应用一次。
- 所有玩法聚合同一归一化 90 分钟 `DixonColesGrid`。
- Football-Data 只作赛程/90 分钟结果 fallback，其赔率列不能进入足球模型。
- 市场缺失不能删除足球预测；合成赔率不能证明模型质量或 ROI。
- 生产命令必须幂等、可恢复、输出结构化诊断，并在验收门禁失败时返回非零退出码。
